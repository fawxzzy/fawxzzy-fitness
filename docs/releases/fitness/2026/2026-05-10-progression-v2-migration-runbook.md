## Pre-apply checks

Run from the repo root:

```powershell
cd C:\ATLAS\repos\fawxzzy-fitness
npm run verify
npm run qa:llel:progression
npx supabase migration list --linked
npm run migration:validate
npm run release:fitness:ready
```

Expected state before apply:

- `verify` passes.
- `qa:llel:progression` passes and refreshes `runtime/fitness/llel-captures/latest/report.json`.
- `migration list --linked` shows the three missing remote versions above.
- `migration:validate` reports those same three missing versions.
- `release:fitness:ready` still fails because migrations are pending and the stacked working tree is not yet release-clean.

If `npx supabase migration list --linked` shows anything other than the three versions above as missing, stop and classify the drift before touching the remote.

## Apply commands

Use the existing repo and Supabase convention:

```powershell
npx supabase migration list --linked
npx supabase db push --include-all --linked
```

Notes:

- `db push --include-all --linked` is the approved apply step in the existing fitness migration docs when local checked-in migrations intentionally need to advance the linked remote.
- The linked remote may require `SUPABASE_DB_PASSWORD` in the shell before `db push` or later dry-run checks can succeed.
- Do not run `supabase migration repair` unless remote schema truth is known and the drift has been explicitly classified as a history-repair case.

## Post-apply checks

After the apply step succeeds, rerun:

```powershell
npm run migration:validate
npm run qa:llel:progression
npm run verify
npm run release:fitness:ready
```

Expected post-apply state:

- `migration:validate` no longer reports the three pending versions.
- `qa:llel:progression` remains green.
- `verify` remains green.
- `release:fitness:ready` can only pass once migration drift is gone, the release draft is present and current, and the working tree is clean.

## Release sequence after migration apply

Use this operator order:

```powershell
npm run release:fitness:prepare
npm run release:fitness:diff
# apply migrations in the order above
npm run migration:validate
npm run qa:llel:progression
npm run verify
npm run release:fitness:ready
# deploy only after readiness passes
npm run release:fitness:record
```
